### Slide 2: The Architectural Problem
**Header**: THE ANTI-PATTERN  
**Title**: Cold Boots & Context-Switching Kills Flow  
**Body**:
Most server-side Dart setups rely on full process restarts (`dart run` restarts) or raw file watchers. 

**The Pain Points**:
- ❌ **3-5 second delay** per change while the Dart VM re-compiles ASTs from scratch.
- ❌ Destroys active TCP connections, local caches, and test states.
- ❌ Forces full-stack Flutter developers back into slow, non-reactive backend iteration cycles.

### Slide 3: The Jetleaf Way — Instant Iteration
**Header**: CLEAN TOOLING  
**Title**: Zero-Config Hot Reload with `jl dev`  
**Body**:
Run your application using the resident `JetleafVM` daemon. It hot-reloads incremental code changes without dropping your server instance or resetting DI Pod state.

### Slide 4: Under the Hood
**Header**: ARCHITECTURE  
**Title**: How `JetleafVM` Achieves Sub-100ms Reloads  
**Body**:
1. **Resident Daemon**: `jl dev` spawns a persistent master process that keeps a standby Dart isolate pre-warmed in memory.
2. **AST Delta Watcher**: Uses file system event channels to compile *only modified AST nodes* to Dart Kernel bytes (`.dill`).
3. **Isolate Hot Swap**: Injects the differential code into the running runtime isolate, preserving singleton Pod states and open database pools while maintaining IoC container integrity.

### Slide 5: Enterprise Best Practice
**Header**: PRO-TIP  
**Title**: Lightning TDD with `jl test --watch`  
**Body**:
Don't wait for your entire test suite to execute after changing a single REST controller or Service Pod.

Use the `JetleafVM` test runner with isolate pre-warming to target affected test files autonomously:

